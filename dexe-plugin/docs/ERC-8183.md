# A DeXe DAO as an ERC-8183 evaluator

[ERC-8183](https://eips.ethereum.org/EIPS/eip-8183) ("Agentic Commerce", Draft) is a
job escrow for agent work. A **client** funds a job, a **provider** submits a
deliverable, and an **evaluator** calls `complete` to pay the provider or `reject`
to refund the client. The spec says the evaluator "MAY be a smart contract", so a
DeXe GovPool can fill the role. The escrow then pays out only after the DAO's
agents vote, and the human validators can still veto.

This recipe uses existing dexe-mcp tools and existing DeXe contracts. There is no
evaluator adapter and no protocol change. It was proven end to end on BSC testnet
(chain 97) on 2026-11-05.

## The flow

| Step | Who | Call |
| --- | --- | --- |
| 1 | operator | `dexe_agent_treasury_create` deploys the DAO: n agents k-of-n, plus human validators ([AGENT-TREASURY.md](AGENT-TREASURY.md)) |
| 2 | client | `escrow.createJob(provider, evaluator = <GovPool>, expiredAt, description, hook)`, then `setBudget` and `fund` |
| 3 | provider | `escrow.submit(jobId, deliverable, 0x)` |
| 4 | agent 1 | `dexe_proposal_create` with `proposalType: "custom_abi"` and `params: { target: <escrow>, signature: "function complete(uint256 jobId, bytes32 reason, bytes optParams)", method: "complete", args: [jobId, reason, "0x"] }`. For a refund, use `reject` instead. |
| 5 | agents 2..k | `dexe_proposal_vote_and_execute` with `isVoteFor: true, autoExecute: true, signerKey: "<agent>"` |
| 6 | human validator | `dexe_proposal_vote_and_execute` with `driveValidatorRound: true, autoExecute: true`. `GovPool.execute` calls the escrow, which is the settle. |

The GovPool is `msg.sender` of `complete`/`reject`, so the escrow's
`onlyEvaluator` check passes. `GovPool.execute → <escrow>.complete` is an
ordinary external call, and the chain-97 SphereX firewall allows it.

### Measured on chain 97

Settings: 3 agents, 2-of-3, quorum 50 %, `duration` 300 s, `durationValidators`
300 s, `executionDelay` 0, `earlyCompletion` on, 1 human validator.

| Job | Verdict | Budget | Submit → settle | Result |
| --- | --- | ---: | ---: | --- |
| 1 | `complete` | 100 tUSD | 41 s | provider 0 → 100, escrow 100 → 0 |
| 2 | `reject` | 40 tUSD | 28 s | client refunded 40, status `Rejected` |
| 3 | `complete` on the fast lane (below) | 25 tUSD | 15 s from proposal to settle | provider 100 → 125, no validator round |
| 4 | none, the job expired | 10 tUSD | — | `claimRefund` after `expiredAt` refunded the client |

## Choose `expiredAt` from the DAO's settings

These voters respond within seconds, and with `earlyCompletion` on the
settlement takes 15–41 s. The **worst case** is when the voting windows run to
the end:

```
expiredAt  >  submit time
            + duration + durationValidators + executionDelay   (of the settings the proposal gets)
            + proposal and tx time
            + margin for slow voters
```

With the demo settings, the worst case is 600 s plus the transaction time.
Production settings are often 1 day plus 1 day, so set `expiredAt` days ahead.
The ERC-8183 reference implementation only requires `expiredAt > now + 5 min`.
That is far too short for a DAO evaluator.

**A late verdict loses.** `claimRefund` cannot be hooked, and anyone may call it
once `block.timestamp >= expiredAt`. Once the client has been refunded, the DAO's
`execute` reverts, and the proposal stays `SucceededFor` for good. This was
verified on 97: a `complete(4)` passed after job 4's refund, and its `execute`
reverted.

## Which settings a proposal gets (the DEFAULT fallback)

The GovPool picks the settings for each proposal at creation, in
`GovPoolCreate._validateProposal` (DeXe-Protocol
`contracts/libs/gov/gov-pool/GovPoolCreate.sol`):

- **L140** `mainExecutor = actionsFor[actionsFor.length - 1].executor`: the
  **last** action decides.
- **L147** `settingsId = govSettings.executorToSettings(mainExecutor)`: an
  executor that is not mapped returns 0, which is DEFAULT.
- **L149–156** `_handleDataForProposal` can force DEFAULT.
- **L298–316** `_handleDataForExistingSettingsProposal` forces it when **any
  earlier action** targets an executor with a different settings id **and** that
  action has `value != 0`, or a selector other than `approve` or
  `setApprovalForAll`.

Verified on 97. In this DAO the escrow is bound to its own slot: 240 s, no
validator round, `quorumValidators` 60 %. The token is not mapped, so it uses
DEFAULT.

| Actions, in order | Settings the proposal got |
| --- | --- |
| `[escrow.complete]` | the escrow slot. It executed on two agent votes, with no validator round. |
| `[escrow.complete, token.transfer(0)]` | DEFAULT. The last action decides, and the token is not mapped. |
| `[token.transfer(0), escrow.complete]` | DEFAULT. It was forced by the earlier non-approve action. |
| `[token.approve(escrow, 0), escrow.complete]` | the escrow slot. `approve` is exempt. |

What this means:

- Executor settings work only as a **looser** lane. Anyone who can create a
  proposal can push it back to DEFAULT by adding one extra action. The reverse
  is not possible.
- The `approve` exemption lets a treasury `approve` of any token ride the fast
  lane. A fast-lane DAO must treat that as a spend.
- A fast lane with `validatorsVote: false` **removes the human veto** for every
  verdict on that escrow. Use it only when a wrong `complete` is cheap.

### Binding the escrow to its own slot on chain 97

On 97, governance cannot bind the slot after deploy. SphereX blocks
`GovPool.execute` both for `GovSettings.addSettings` ([#36](UPSTREAM-ISSUES.md))
and for `GovSettings.changeExecutors`. The block also applies when
`changeExecutors` is the only action, or when it is bundled with
`editSettings`, and the error is `"SphereX error: disallowed tx pattern"`. The
binding must happen at deploy. Put the escrow first in
`settingsParams.additionalProposalExecutors` and insert its settings at index 3
of `proposalSettings`, because
`GovSettings` requires `additionalProposalExecutors.length + 3 ==
proposalSettings.length`. `dexe_agent_treasury_create` has no option for this
today. The demo decoded the `dryRun` payload, edited it, and broadcast the
result.

## Caveats

- **The escrow is your own.** ERC-8183 is a Draft with no canonical deployment.
  The demo escrow was written to the spec text, is unaudited and testnet-only,
  has no fees, and was run with `hook = address(0)`. The reference
  implementation differs from the spec text in four ways:
  - `fund` has no `expectedBudget`;
  - `setBudget` can be called only by the provider;
  - `fund` reverts after expiry;
  - it adds an evaluator fee.
- **Quorum on 97 counts turnout.** An AGAINST vote counts toward quorum, so an
  agent that votes against can still help a proposal pass. See
  [AGENT-TREASURY.md](AGENT-TREASURY.md).
- **Nothing on chain ties a verdict to the deliverable.** The agents must read
  the deliverable off-chain and decide. Put the deliverable hash in the proposal
  description so the validators can check it.
- **One proposal per job.** There is no batching here. Each verdict pays the
  normal deposit, create, vote, and execute gas.
